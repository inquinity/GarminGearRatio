## What I found

**The app-type question is effectively already answered by your two reference codebases:**

- **`emtb`** (in `reference/emtb/`) is a `type="datafield"` app that declares the `BluetoothLowEnergy` permission and connects as BLE central to the *same* `0x18EF`/`2AC1` Shimano service your SC-EM800 uses. So a **data field can own a BLE connection to your bike** — this is proven, not theoretical.
- **GearRatio** is also a `type="datafield"` (targeting `edge1050`, your hardware), and it already demonstrates the two things you'll need beyond BLE: an on-device config **wizard** via `getSettingsView()` (→ your "config page") and a `GearConfig` model for tooth counts (→ your "gear configuration" data).

**Data Field is the right app type** because it's the *only* type that renders inside the activity's data-page rotation — which is exactly what "replace Garmin's built-in Di2 data pages" means. Widgets and device apps run standalone, outside the ride.

**The one hard constraint that shapes everything:** only one Connect IQ app can own the BLE connection to the SC-EM800 at a time (and BLE profiles are capped at 3). So the design must funnel all data through **one BLE-owning app**. Your four requirements then map to **render modes + a settings wizard inside that single data field**:

| Requirement | How it's delivered in a data field |
|---|---|
| Config page | `getSettingsView()` wizard (GearRatio pattern) + Garmin Connect app settings |
| Test information page | A "debug" render mode drawing name/value pairs for every decoded field (emtb's `labelsDict`/`values` pattern) |
| Di2-replacement data fields | The normal render mode(s): gear, ratio, assist mode, battery… |
| Gear configuration page | A render mode drawing drivetrain topology + tooth counts (reuse `GearConfig`) |
